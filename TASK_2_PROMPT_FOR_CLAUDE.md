# Промпт для Claude Code — доработка действующего приложения «Фокус»

Прочитай файлы в корне репозитория: `CLAUDE.md`, `README.md`, `TASK_2_REQUIREMENTS_BASE.md`, `FILE_IMPORT_AND_STORAGE.md` и `TASK_2_CHANGE_REQUESTS.md` (если какой-то файл отсутствует, сообщи об этом, но продолжай с доступными материалами). Сначала изучи существующий код и GitHub Pages workflow.

**Главный источник актуальных правок — `TASK_2_CHANGE_REQUESTS.md`. Он имеет приоритет над базовой спецификацией, если требования расходятся.** Базовая спецификация продолжает действовать для всего, что не изменено этим документом.

Ты работаешь над уже существующим прототипом. Не создавай проект с нуля, не удаляй работающие функции и не меняй стек без технической необходимости. Не добавляй авторизацию, Supabase, backend или облачное хранилище. Приложение должно остаться статическим сайтом, который публикуется на GitHub Pages. Используй LocalStorage/IndexedDB по требованиям.

## Порядок работы

1. Проведи аудит репозитория: текущий стек, маршруты/экраны, стили, данные и их форматы, таймеры, импортеры книг, тесты, сборка и настройка base path GitHub Pages.
2. Составь компактный план с конкретными файлами и зависимостями, которые затронешь. Отметь риски обратной совместимости.
3. Не останавливайся после плана. Реализуй требования из `TASK_2_CHANGE_REQUESTS.md`, сохранив функциональность базовой спецификации там, где она не отменена.
4. Начни с чистых/проверяемых модулей: генераторы данных, токенизация текста, расчёт WPM, проверка порядка ответов и результаты. Покрой эти функции тестами там, где тестовая инфраструктура доступна.
5. Сделай UI удобным для касаний на iPad: достаточно крупные цели касания, адаптивные сетки, отсутствие случайного вертикального скролла во время игр, корректные состояния фокуса/выбора и ясные ошибки.
6. Не вставляй пользовательские DOCX/EPUB как доверенный HTML напрямую. Не отправляй текст книг во внешние API. Храни импортированные книги и позиции чтения локально через IndexedDB.
7. Проверь таймеры на фоне и при переключении вкладки: ориентируйся на абсолютные временные метки, а не на число вызовов `setInterval`.
8. Запусти доступные unit-тесты, lint, typecheck и production build. Устрани ошибки. Проверь правильную публикационную конфигурацию для GitHub Pages.
9. Если какое-то требование конфликтует с реальным ограничением текущей архитектуры, реализуй ближайший безопасный вариант и точно опиши ограничение. Не имитируй функции, которые не работают.
10. В конце выдай отчёт: реализованные изменения, затронутые файлы, фактически выполненные проверки, результаты, незавершённые пункты и инструкции по проверке на опубликованном сайте.

Работай непосредственно в текущем репозитории. Подготавливай ясные изменения, которые легко проверить и сохранить в Git. Не перезаписывай и не коммить существующие пользовательские изменения без необходимости; если требуется commit, сначала сообщи, какие файлы будут включены.
